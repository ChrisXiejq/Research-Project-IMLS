# 实验代码全链路讲解

本文档用于从宏观到微观解释当前 `Research-Project-IMLS` 仓库中的 CARLA intersection 复现实验代码。目标是帮助理解：实验在复现什么、每个模块做什么、配置如何进入仿真、SMPC 如何被调用、结果如何被保存和评估，以及每个模块对应的专业术语。

## 1. 实验总体目标

当前实验围绕论文 `Predictive Control for Autonomous Driving With Uncertain, Multimodal Predictions` 的 CARLA intersection 场景进行复现。核心任务是在一个带目标车辆的路口场景中，让 ego vehicle 根据目标车辆的多模态未来轨迹预测，使用 SMPC 控制器安全、平滑地通过路口。

当前实验不是单纯播放轨迹，而是一个闭环控制系统：

1. CARLA 生成道路、车辆和传感器环境。
2. 系统在每个仿真步读取 ego vehicle 和 target vehicle 的状态。
3. MultiPath/GMM 模型给出 target vehicle 的多模态预测。
4. SMPC 根据预测、风险约束和参考轨迹求解控制量。
5. 控制量被转换为 CARLA 的 throttle/brake/steer 并施加到 ego vehicle。
6. 仿真继续推进，直到 ego 完成任务或达到最大步数。
7. 后处理脚本将 rollout 结果转换为论文可用的指标表和图。

专业词汇：

- **Ego Vehicle / EV**：被控制的主车，即当前实验中需要通过路口的车辆。
- **Target Vehicle / TV**：交通参与者或障碍车辆，是 ego 需要预测和避让的对象。
- **Closed-loop Control**：闭环控制，每个仿真步都根据最新状态重新求解控制。
- **Open-loop Control**：开环控制，控制策略不显式依赖未来状态反馈，通常作为 ablation baseline。
- **Ablation Study**：消融实验，通过去掉或固定某个模块来验证该模块的作用。
- **Reproduction Pipeline**：复现实验流水线，指从配置、运行、保存结果到自动评估的完整链路。

## 2. 代码分层架构

当前实验代码可以分为七层：

| 层级 | 主要文件/目录 | 职责 |
|---|---|---|
| 实验入口层 | `run_all_scenarios.py`、`run_modern_reproduction.sh`、`run_full_reproduction.sh` | 解析命令行参数，批量组合 scenario/init/policy，创建结果目录 |
| 场景配置层 | `core/scripts/carla/scenarios/*.json`、`scenarios/inits/*.json`、`intersection_01.csv` | 定义地图、车辆、起终点、初速度、可视化参数 |
| CARLA 仿真层 | `run_intersection_scenario.py` | 连接 CARLA、加载 Town05、生成车辆、推进同步仿真 |
| 预测层 | `AgentHistory`、`SemBoxRasterizer`、`DeployMultiPath` | 根据历史状态生成 target vehicle 的 GMM 多模态预测 |
| 策略层 | `smpc_agent.py` | 读取状态和预测，管理参考轨迹，调用 SMPC 求解器，输出控制 |
| 优化器层 | `mpc_utils.py` | 实现参考轨迹生成、closed-loop SMPC、open-loop SMPC、风险约束和求解逻辑 |
| 评估层 | `compute_scenario_results.py`、`evaluation/closed_loop_metrics.py` | 加载 rollout，生成 `df_full.csv`、`df_final.csv`、`paper_metrics_summary.md` 等 |

专业词汇：

- **Layered Architecture**：分层架构，把入口、配置、仿真、控制、优化和评估拆分到不同模块。
- **Batch Runner**：批量运行器，负责自动执行多个实验组合。
- **Scenario Configuration**：场景配置，定义仿真中的地图、车辆和任务。
- **Policy**：策略，指给定当前状态后输出控制动作的控制逻辑。
- **Backend Solver**：后端求解器，例如 Gurobi 或 IPOPT，用于求解优化问题。

## 3. 宏观执行链路

典型运行命令如下：

```bash
cd core/scripts/carla

python run_all_scenarios.py \
  --scenario_glob "scenario_01.json" \
  --init_glob "ego_init_0[1-5].json" \
  --policies smpc_var_risk smpc_open_loop smpc_fixed_risk \
  --solver_backend gurobi \
  --risk_profile upstream_code \
  --with_notv \
  --with_notv_cl \
  --enable_camera_viz
```

执行顺序如下：

1. `run_all_scenarios.py` 找到 `scenario_01.json`。
2. 找到 `ego_init_01.json` 到 `ego_init_05.json`。
3. 对每个 `scenario × init` 组合运行：
   - `notv`
   - `notv_cl`
   - `smpc_var_risk`
   - `smpc_open_loop`
   - `smpc_fixed_risk`
4. 每个子实验调用 `RunIntersectionScenario.run_scenario()`。
5. 每个子实验写入一个目录，例如：
   - `core/results/20260524_133505/scenario_01_ego_init_02_smpc_var_risk/`
6. 批量运行结束后自动调用 `compute_scenario_results.py` 做后处理。

专业词汇：

- **Scenario Grid**：实验网格，指 `scenario × initial condition × policy` 的组合。
- **Initial Condition**：初始条件，例如 ego 的初始速度和起始纵向偏移。
- **Rollout**：一次完整仿真轨迹，从初始状态开始直到完成或失败。
- **Timestamped Results Directory**：带时间戳的结果目录，用于隔离每次实验输出。

## 4. 实验入口层：`run_all_scenarios.py`

`core/scripts/carla/run_all_scenarios.py` 是当前最重要的批量实验入口。

它主要做五件事：

1. 解析命令行参数。
2. 匹配 scenario JSON 和 ego init JSON。
3. 为每个 policy 创建子实验目录。
4. 调用 `run_with_tvs()` 或 `run_without_tvs()` 执行仿真。
5. 写入 batch summary 并触发后处理。

关键参数：

| 参数 | 含义 |
|---|---|
| `--scenario_glob` | 匹配场景文件，例如 `scenario_01.json` |
| `--init_glob` | 匹配 ego 初始条件文件，例如 `ego_init_0[1-5].json` |
| `--policies` | 要测试的控制策略列表 |
| `--solver_backend` | SMPC 求解后端，主实验使用 `gurobi` |
| `--risk_profile` | 风险约束口径，当前常用 `upstream_code` |
| `--with_notv` | 额外运行无 target vehicle baseline |
| `--with_notv_cl` | 额外运行无 target vehicle closed-loop/centerline baseline |
| `--enable_camera_viz` | 启用 CARLA 相机并保存 AVI 视频 |
| `--skip_postprocess` | 跳过自动指标生成 |

`run_all_scenarios.py` 中的 policy 映射：

| Policy 名称 | 实验含义 |
|---|---|
| `notv` | 无目标车辆 baseline，用于检查基础路线是否可完成 |
| `notv_cl` | 无目标车辆 closed-loop/centerline baseline，用于轨迹参考和对照 |
| `smpc_var_risk` | 可变风险 SMPC，对应论文 Proposed 方法方向 |
| `smpc_fixed_risk` | 固定风险 SMPC，是 variable-risk 的消融对照 |
| `smpc_open_loop` | 开环 SMPC 消融实验，用于比较反馈结构的作用 |

专业词汇：

- **Policy Sweep**：策略扫描，在相同场景下依次测试多个控制策略。
- **Baseline**：基线方法，用于衡量主方法是否真的带来改进。
- **Risk Profile**：风险配置口径，决定 chance constraint 的收紧程度。
- **Post-processing**：后处理，把原始仿真轨迹转换为指标、表格和图。

## 5. 场景配置层

场景配置主要在：

- `core/scripts/carla/scenarios/scenario_01.json`
- `core/scripts/carla/scenarios/intersection_01.csv`
- `core/scripts/carla/scenarios/inits/ego_init_*.json`

### 5.1 Scenario JSON

`scenario_01.json` 定义：

1. CARLA 地图，例如 `Town05`。
2. 天气、FPS、路口 CSV。
3. 可视化相机参数。
4. ego vehicle、target vehicle、static vehicle。
5. 每辆车的车型、颜色、起终点、速度和 policy。

其中 `vehicle_params` 是最关键的部分。它定义了：

- 哪辆车是 ego。
- 哪辆车是 target。
- 哪些车是 static obstacle。
- 每辆车从哪个路口节点出发，到哪个节点结束。
- 起点和终点的横向/纵向偏移。
- `nominal_speed` 和 `init_speed`。
- MPC/SMPC 参数，例如 horizon `N`、时间步长 `dt` 和 mode 数量。

### 5.2 Init JSON

`scenarios/inits/ego_init_01.json` 等文件通常只覆盖 ego 的少量初始参数：

- `start_longitudinal_offset`
- `init_speed`

这使得同一个 scenario 可以在不同 ego 初始速度和起点偏移下重复测试。

### 5.3 Intersection CSV

`intersection_01.csv` 定义路口几何结构。代码会根据 CSV 中的路口节点生成路径、起终点和参考轨迹。

专业词汇：

- **Map**：CARLA 地图，例如 `Town05`。
- **Waypoint**：道路上的参考点。
- **Route**：车辆需要跟踪的道路路径。
- **Longitudinal Offset**：沿道路前进方向的偏移。
- **Lateral Offset**：相对车道中心线左右方向的偏移。
- **Nominal Speed**：期望巡航速度。
- **Static Obstacle**：静态障碍物，不参与动态预测。

## 6. CARLA 仿真层：`run_intersection_scenario.py`

`core/scripts/carla/scenarios/run_intersection_scenario.py` 负责真正连接 CARLA 并运行单次 rollout。

### 6.1 初始化流程

`RunIntersectionScenario.__init__()` 大致执行：

1. 保存参数。
2. 连接 CARLA client。
3. 加载地图 `Town05`。
4. 设置同步仿真模式。
5. 生成 ego、target、static vehicles。
6. 给 ego vehicle 绑定 policy。
7. 初始化预测模型和可视化模块。

### 6.2 主仿真循环

`run_scenario()` 是单次实验的主循环。每一步大致如下：

1. `world.tick()` 推进 CARLA。
2. 获取每个 actor 的状态。
3. 更新 target vehicle 历史轨迹。
4. 调用 MultiPath 预测 target vehicle 未来轨迹。
5. 构造 `pred_dict`。
6. 调用 ego policy 的 `run_step(pred_dict)`。
7. 将 policy 输出的控制施加到车辆。
8. 记录状态、控制、可行性和求解时间。
9. 判断是否完成任务。
10. 仿真结束后保存 `scenario_result.pkl`。

专业词汇：

- **Synchronous Simulation**：同步仿真，每一步显式 tick，保证控制和仿真时间对齐。
- **Actor**：CARLA 中的实体，例如车辆、传感器。
- **VehicleControl**：CARLA 的底层控制对象，包括 throttle、brake、steer。
- **Tick**：仿真的一个离散时间步。
- **State Logging**：状态记录，用于后处理分析。

## 7. 预测层：MultiPath/GMM 预测

当前预测链路在 `RunIntersectionScenario._make_predictions()` 附近完成。

主要组件：

| 组件 | 作用 |
|---|---|
| `AgentHistory` | 保存 target vehicle 历史状态 |
| `SemBoxRasterizer` | 将局部交通环境转成模型输入栅格 |
| `DeployMultiPath` | 加载 MultiPath 模型并输出未来轨迹分布 |
| `mode_probs` | 每个预测模态的概率 |
| `mus` | 每个模态每个未来时间步的位置均值 |
| `sigmas` | 每个模态每个未来时间步的协方差 |

MultiPath 输出的是 GMM 形式的多模态预测：

- 车辆可能直行。
- 车辆可能轻微偏移。
- 车辆可能有不同速度/轨迹变化。

SMPC 不直接假设 target vehicle 只有一条确定轨迹，而是把多个可能未来都纳入风险约束。

专业词汇：

- **Multimodal Prediction**：多模态预测，表示未来可能有多种合理轨迹。
- **Gaussian Mixture Model / GMM**：高斯混合模型，用多个高斯分布表示不确定未来。
- **Mode Probability**：每个预测模态发生的概率。
- **Mean Trajectory**：预测轨迹均值。
- **Covariance Matrix**：协方差矩阵，表示预测位置的不确定性形状和大小。
- **Rasterization**：栅格化，把地图和车辆历史编码成图像/张量输入。

## 8. 策略层：`smpc_agent.py`

`core/scripts/carla/policies/smpc_agent.py` 是 ego vehicle 的控制策略层。它连接 CARLA 仿真和 SMPC 优化器。

### 8.1 `SMPCAgent.__init__()`

初始化时完成：

1. 读取车辆参数。
2. 设置 horizon、dt、mode 数量。
3. 判断 policy 类型：
   - variable-risk
   - fixed-risk
   - open-loop
   - OBCA variant
4. 初始化 `RefTrajGenerator`。
5. 初始化 SMPC 求解器。
6. 初始化 debug 输出状态。

### 8.2 `SMPCAgent.run_step()`

这是每个仿真步都会调用的主函数。

执行顺序：

1. 从 CARLA 读取 ego 当前状态。
2. 转换坐标系。
3. 将 ego 状态投影到 Frenet frame。
4. 判断是否完成任务。
5. 生成或恢复参考轨迹。
6. 处理 target vehicle 预测。
7. 构造 `update_dict`。
8. 调用 SMPC 的 `update()`。
9. 调用 SMPC 的 `solve()`。
10. 将优化控制转换为 CARLA 控制。
11. 写入 debug JSONL。

### 8.3 `update_dict`

`update_dict` 是策略层和优化器层之间最重要的数据接口。它包含：

- ego 初始误差：`dx0`、`dy0`、`dpsi0`、`dv0`
- reference state：`x_ref`、`y_ref`、`psi_ref`、`v_ref`
- reference input：`a_ref`、`df_ref`
- linearization trajectory：`x_lin`、`y_lin`、`psi_lin`、`v_lin`
- target vehicle 当前状态：`x_tv0`、`y_tv0`
- target vehicle GMM：`mus`、`sigmas`、`probs`
- 上一帧控制：`u_prev`
- 车辆形状矩阵：`tv_shapes`

专业词汇：

- **Frenet Frame**：沿参考路径建立的坐标系，常用 `s` 表示沿路径距离，`ey` 表示横向偏差，`epsi` 表示航向误差。
- **Reference Trajectory**：参考轨迹，控制器希望 ego 跟踪的轨迹。
- **Linearization Trajectory**：线性化轨迹，用于把非线性车辆模型近似成线性时变模型。
- **Control Input**：控制输入，通常包括加速度 `a` 和前轮转角 `df`。
- **Low-level Control**：低层控制，将高层加速度/转角转换成 throttle/brake/steer。

## 9. SMPC 优化层：`mpc_utils.py`

`core/scripts/carla/utils/mpc_utils.py` 是实验中最核心的数学优化代码。

### 9.1 `RefTrajGenerator`

`RefTrajGenerator` 用于生成动力学可行的参考轨迹。它会考虑：

- 车辆动力学。
- 速度上下界。
- 加速度和转角上下界。
- 输入变化率约束。
- waypoint tracking cost。

它的作用不是避障，而是给 SMPC 提供一个合理、平滑、可跟踪的参考。

专业词汇：

- **Feasible Reference**：满足车辆动力学和输入约束的参考轨迹。
- **Input Rate Constraint**：输入变化率约束，限制加速度和转角变化过快。
- **Tracking Cost**：跟踪代价，惩罚车辆偏离参考轨迹。

### 9.2 `SMPC_MMPreds`

`SMPC_MMPreds` 是 closed-loop risk-aware SMPC 的主要实现。

它处理：

1. EV 线性时变动力学。
2. TV 多模态预测。
3. chance constraint。
4. risk allocation。
5. collision avoidance。
6. 输入和状态约束。
7. Gurobi conic optimization。

主要方法：

| 方法 | 作用 |
|---|---|
| `_get_LTV_EV_dynamics()` | 构造 ego vehicle 的线性时变动力学矩阵 |
| `_set_TV_ref()` | 将 target vehicle GMM 转成优化器参数 |
| `_add_constraints_and_cost()` | 添加约束和目标函数 |
| `update()` | 每步写入最新状态、预测和参考 |
| `solve()` | 调用 Gurobi 求解控制量 |

### 9.3 `SMPC_MMPreds_OL`

`SMPC_MMPreds_OL` 是 open-loop ablation。它的作用是测试没有 closed-loop feedback 结构时系统表现如何。

当前版本中，open-loop 做了工程化稳定：

- 使用 `risk_profile=upstream_code` 对齐原仓风险口径。
- 使用 `collision_slack` 软化碰撞约束，避免边界情况下直接 `INF_OR_UNBD`。
- fallback 从硬刹改为参考输入，避免失败级联。

这使 open-loop 能完成任务，但它不应被解释为完全 hard-constraint 成功。

专业词汇：

- **Stochastic Model Predictive Control / SMPC**：随机模型预测控制，在优化中显式考虑不确定性。
- **Chance Constraint**：机会约束，以概率形式要求碰撞风险低于阈值。
- **Risk Allocation**：风险分配，将总风险预算分配到不同时间步、目标车或预测模态。
- **SOCP / Second-order Cone Programming**：二阶锥规划，Gurobi 可求解的一类凸优化问题。
- **Slack Variable**：松弛变量，用于软化约束，使问题在边界情况下仍可求解。
- **Fallback Control**：求解失败时采用的后备控制策略。

## 10. 风险配置与论文复现口径

当前代码支持两种风险口径：

| Risk profile | 含义 | Tightening |
|---|---|---|
| `upstream_code` | 更贴近原仓 CARLA 代码口径 | `1.64` |
| `paper_eps_002` | 更贴近论文文字中 epsilon=0.02 的口径 | 约 `2.054` |

当前主要实验使用：

```bash
--risk_profile upstream_code
```

这是因为原仓实际 CARLA intersection 代码中使用的 tightening 更接近 `1.64`。但论文文字和原仓代码之间存在一定口径差异，因此最终 dissertation 中需要明确说明采用的是哪个 profile。

专业词汇：

- **Tightening**：约束收紧系数，用于把概率约束转成确定性安全边界。
- **Confidence Level**：置信水平，表示约束满足概率。
- **Reproduction Fidelity**：复现保真度，表示当前实现和原论文/原仓的一致程度。

## 11. 完成判据与 Reference Recovery

当前 completion 不是只看 CARLA goal，而是同时记录：

- `s_to_end`：距离 reference path 终点还有多远。
- `goal_dist`：距离 CARLA goal coordinate 还有多远。
- `ey`：横向误差。
- `lateral_ok`：横向误差是否在阈值内。
- `completion_valid`：是否满足有效完成。

这样做是因为 CARLA goal coordinate 和 reference path 终点不一定完全重合。如果只看一个指标，容易出现“看似完成但实际偏离路径”的假完成。

Reference recovery 是当前代码中的重要工程保护：

- 如果横向误差过大，代码不会继续用偏离后的车辆状态生成新 reference。
- 它会恢复 global reference。
- 并强制使用 reference slice 做 linearization。

专业词汇：

- **Completion Criterion**：任务完成判据。
- **Goal Distance**：当前位置到目标坐标点的欧氏距离。
- **Path Progress**：沿参考路径的进度。
- **Lateral Error**：车辆相对参考路径的横向偏差。
- **Reference Recovery**：参考轨迹恢复机制，用于避免车辆偏离后把错误轨迹固化为新参考。

## 12. Debug 输出链路

每个 SMPC 子实验目录通常包含：

| 文件 | 含义 |
|---|---|
| `smpc_debug_setup.json` | 初始化信息，例如 policy、risk profile、N、dt、SMPC 类型 |
| `smpc_debug_steps.jsonl` | 每步控制和求解 debug 记录 |
| `smpc_first_failure.json` | 第一次求解失败时的完整上下文 |
| `smpc_debug_latest_failure.json` | 最新一次失败上下文 |
| `smpc_completion.json` | 第一次有效完成时的状态和 completion metrics |

`smpc_debug_steps.jsonl` 每行是一个 JSON，包含：

- vehicle state
- prediction summary
- reference status
- solver result
- applied control
- completion metrics
- relative geometry to TV
- slack 和 solver failure 信息

专业词汇：

- **JSONL**：每行一个 JSON 的日志格式，适合逐步追加和流式解析。
- **Solver Status**：优化器状态，例如 `OPTIMAL`、`SUBOPTIMAL`、`INF_OR_UNBD`。
- **Infeasible or Unbounded / INF_OR_UNBD**：优化器无法判断问题是不可行还是无界，通常表示约束冲突或数值问题。
- **Diagnostic Logging**：诊断日志，用于定位失败原因，而不只是保存最终结果。

### 13.2 核心指标

| 指标 | 含义 |
|---|---|

专业词汇：

- **Feasibility Rate**：优化问题成功求解的比例。

- **Jerk**：加速度变化率，越大表示控制越不平滑。
- **Hausdorff Distance**：两条轨迹集合之间的最大最近距离，用于衡量路径偏差。

## 14. 当前最新实验结果如何理解

以 `core/results/20260524_133505` 为例，当前进行了：

- 1 个 intersection scenario。
- 5 个 ego initial conditions。
- 5 类 policy。
- 共 25 个 rollout。

当前核心结论：

- 所有 rollout 都完成了 intersection task。
- `smpc_var_risk` 和 `smpc_fixed_risk` 能在多初始条件下完成任务，说明主闭环 SMPC pipeline 已经跑通。
- `smpc_open_loop` 也完成任务，但显著依赖 `collision_slack`，因此应视作 diagnostic ablation，而不是完全 hard-constraint baseline。
- `smpc_var_risk/fixed_risk` 的 path deviation 仍偏大，说明 reference tracking 和 linearization 还需要优化。
- `smpc_var_risk` 在部分 initial condition 有少量 `INF_OR_UNBD`，说明可变风险版本仍需继续修正稳定性。

专业词汇：

- **Preliminary Results**：初步结果，可以证明 pipeline 和方向有效，但还不能作为最终结论。
- **Pilot Experiment**：小规模试验，用于验证方法和发现问题。
- **Quantitative Agreement**：数值一致性，指当前结果是否接近原论文的数值水平。
- **Diagnostic Ablation**：用于诊断问题的消融实验，不一定完全等价于论文最终 baseline。

## 15. 当前实现与原论文的关系

当前代码的实验思路与原论文一致：

- 复现 CARLA intersection 场景。
- 使用 multimodal target vehicle prediction。
- 使用 SMPC 做 ego vehicle 控制。
- 比较 proposed variable-risk、fixed-risk、open-loop、no-TV baselines。
- 生成 completion、safety、comfort、solve time 和 path deviation 等指标。

但当前实现不是完全无偏的最终复现：

- open-loop 为了稳定运行加入了 `collision_slack`。
- completion diagnostics 比原始代码更严格。
- reference recovery 是为了避免偏离轨迹被固化而加入的工程保护。
- 当前实验规模仍是小规模 pilot。

因此对外表述应使用：

- “reproduction-oriented implementation”
- “preliminary reproduction pipeline”
- “multi-initialisation pilot”

不应直接称为：

- “fully reproduced the paper results”
- “quantitatively matched the original paper”

## 17. 后续代码优化重点

当前最值得继续优化的方向有三类：

1. 降低 `smpc_var_risk/fixed_risk` 的 path deviation。
2. 减少 `smpc_var_risk` 的 `INF_OR_UNBD` solver failure。
3. 区分 hard-constraint open-loop 和 soft-constraint diagnostic open-loop。

建议后续逐步做：

1. 对 tracking cost、heading cost、velocity cost 和 input smoothness cost 做小范围调参。
2. 继续记录和分析 `max_abs_ey_debug`、`forced_reference_linearization_frac`。
3. 保留 open-loop soft 版本，但额外实现一个原始 hard open-loop baseline。
4. 在 `scenario_01 + ego_init_01~05` 稳定后，再扩展到更多 init 和更多 scenario。

## 18. 一句话总结

当前实验代码已经形成了一个较完整的 CARLA intersection SMPC 复现流水线：`run_all_scenarios.py` 负责批量实验，`run_intersection_scenario.py` 负责单次 CARLA 闭环仿真，`smpc_agent.py` 负责将状态和预测转成优化问题，`mpc_utils.py` 负责求解 SMPC，`compute_scenario_results.py` 负责生成论文式指标。当前 pipeline 已经能产出可汇报的 preliminary results，但仍需要继续优化路径偏差、求解稳定性和 open-loop baseline 的严格复现一致性。
